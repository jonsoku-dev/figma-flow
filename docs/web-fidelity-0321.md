# 웹 가져오기 실측 · 0.32.1

Magic UI Portfolio와 CodeForge의 실제 로컬 페이지를 브라우저에서 열고, 같은 뷰포트의 측정값과 PNG를 저장했다. Figma Flow의 자체 개발 플러그인으로 Figma Design 프레임을 만들고 편집 가능한 텍스트의 범위를 다시 읽었다. 인수 조건은 [편집 가능한 웹 그래프](../specs/editable-web/graph.json), 사용 방법은 [캡처 가이드](web-design-capture.md)에 있다. 템플릿 원본·사진·작업 파일의 비공개 식별자는 배포본에 포함하지 않는다.

## CSS letter spacing

각 제목을 두 번 가져왔다. 대조 프레임에는 자간 필드만 생략했다. 브라우저에서 측정한 텍스트 범위의 너비와 Figma TEXT 노드의 자연 너비를 CSS px와 Figma px 기준으로 비교했다. 화면 미리보기의 확대 배율로 구한 수치가 아니다.

| 화면과 텍스트 | 브라우저 너비 | 기본 자간 Figma | 측정 자간 Figma | Figma에서 다시 읽은 자간 |
| --- | ---: | ---: | ---: | ---: |
| Portfolio · Hero 제목 1행 | 254.55 | 290 | 256 | −2.4 px |
| CodeForge · Hero 제목 1행 | 551.17 | 611 | 554 | −3 px |
| CodeForge · Hero 제목 2행 | 449.17 | 503 | 452 | −3 px |

Portfolio는 1440 × 900 뷰포트(문서 너비 1425), CodeForge는 너비 1265 × 높이 720의 캡처 레이아웃을 사용했다. 두 프레임은 각각 91개, 63개의 편집 가능한 하위 노드를 포함했다. 두 화면에서 글꼴 대체는 보고되지 않았다. 사용자가 자간을 지정하지 않은 텍스트와 이전 그래프는 기존 기본값을 사용한다. 가져오기를 반복했을 때 두 프레임의 ID가 유지됐다. 글자 가장자리, 줄 높이와 브라우저 합성 배경까지 픽셀 단위로 같다는 뜻은 아니다.

### 같은 자간의 버튼 재사용

직군 간 인계에서 중요한 것은 같은 스타일을 한 곳에서 수정할 수 있는지다. 브라우저에서 동일한 크기·글꼴·색을 가진 버튼 네 개를 측정했다. 레이블이 다른 두 버튼은 +1.5 px, 나머지 두 버튼은 −0.75 px였다. Figma에서 두 메인 컴포넌트와 두 인스턴스가 생성됐고, 각 인스턴스는 같은 자간의 메인을 가리켰다. 두 번째 적용과 별도 읽기에서 메인·인스턴스 ID를 다시 대조했다. Figma 속성 패널에서 −0.75 px 메인을 3 px로 직접 바꾸자 같은 프레임을 읽은 결과가 `changed`가 됐다. −0.75 px로 복원한 뒤 같은 ID가 `current`가 됐다. 이는 서로 다른 자간의 버튼을 잘못된 메인에 합치거나, 레이블 문자열마다 새 메인을 만드는 경우를 구분한다.

같은 검사를 포크에서 실행하려면 해당 작업의 비공개 그래프와 화면 범위 읽기 결과를 사용한다. 각 `--pair`는 브라우저 그래프의 메인·인스턴스 요소 ID 쌍이다.

```sh
python3 tests/verify_web_typography.py controls-graph.json restored-readback.json \
  --pair el-7 el-8 --pair el-9 el-10 --drift-readback changed-readback.json --drift-element el-9
```

## Raster preview

브라우저에서 교차 출처 canvas를 직접 읽지 못해 저장한 원본 뷰포트 스크린샷의 120 × 60 CSS px 영역을 사용했다. 양 버전의 Figma 출력 너비는 480 px였고 비교한 영역은 180 × 90 px였다. 같은 불투명 빨간색 RGB(231, 0, 11)의 픽셀 수를 세었다.

| Figma 내보내기 | 첫 적용 | 같은 프레임 재적용 |
| --- | ---: | ---: |
| 0.32.0 | 0 | 13,500 |
| 0.32.1 | 13,500 | 13,500 |

0.32.1의 첫 PNG와 두 번째 PNG는 전체 RGB 픽셀이 같았고, 0.32.0의 두 번째 PNG와도 일치했다. 영역의 색을 세는 것은 이 표본의 독립 검증 방법이다. 플러그인은 색상 수로 이미지 성공 여부를 추정하지 않는다. 단색 이미지도 정상 입력이다.

## 증거의 범위

별도 로그인 Chrome에서 두 웹 프레임과 캔버스 프레임을 각각 열어 선택된 레이어 이름과 노드 ID를 확인했다. 데스크톱은 재연결까지 일부 변경이 동기화되지 않는다는 메시지를 여전히 표시했다. 세 프레임은 클라우드에서 관측했지만 파일의 다른 모든 편집까지 저장됐는지는 확인되지 않았다.

회귀 기준은 [그래프 검증](../tests/test_web_design_tracking.py)과 [최초 내보내기](../tests/test_web_design.cjs)에 있다. [미리보기 조건 검사](../tests/test_web_design_preview.cjs)는 이미지가 없는 경우, 기존 프레임, 원본 영상과 대체 이미지의 처리 차이를 확인한다. 새 영상 업로드, 모든 웹 폰트 및 임의의 Figma 문서에서의 렌더 완료는 이번 표본으로 검증하지 않았다.
