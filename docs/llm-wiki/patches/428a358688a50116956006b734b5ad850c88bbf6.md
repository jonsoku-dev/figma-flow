# feat: share unchanged carousel artwork through native image components

## 문제와 계기

캐러셀 상태 4개는 같은 대시보드 이미지를 보여 주지만, 상태 프레임마다 독립 이미지 노드로 만들어졌다. 그래서 Design에서 한 상태의 이미지를 고쳐도 나머지 상태는 따라오지 않았다. 수정 전 Figma 적용 영수증에는 COMPONENT와 INSTANCE가 하나도 없었다.

## 결과 동작

정본 graph의 image 요소에 선택 항목인 componentKey(길이 제한 문자열)를 둘 수 있다. web-carousel 결합은 모든 상태에 정확히 한 번씩, 같은 모양으로 나오는 이미지에만 graph ID·frameKey·시그니처에서 결정적으로 유도한 `carousel-image-…` 키를 부여한다. 같은 모양이란 자산 SHA-256·MIME·objectFit·크기·paint가 같고 조상 프레임의 상자·clipping·paint도 같다는 뜻이다. 결합 결과에는 `shared_image_main_count`를 보고한다. 플러그인은 첫 등장에 IMAGE fill을 가진 메인 컴포넌트를 만들고, 다른 상태에는 그 인스턴스를 둔다. 읽기에서 인스턴스와 메인의 패밀리 키가 다르면 실패한다. Python과 JS 모두 패밀리가 2회 이상, 화면당 한 번, 같은 시그니처가 아니면 쓰기 전에 거부한다.

## 변경 파일과 인터페이스

## 설계 이유와 출처

보이는 결과가 같다는 것이 시그니처로 확인될 때만 컴포넌트로 묶는다. 그래서 크기·맞춤·잘림이 다른 이미지가 한 메인으로 합쳐져 모양이 바뀌는 일이 없다. 키를 graph 내용에서 유도하므로 같은 입력은 같은 패밀리를 얻고, 이미 componentKey가 있는 요소는 다시 지정하지 않는다. 인스턴스에는 이미지 paint를 다시 쓰지 않아 메인을 고치면 모든 상태에 전파된다. 가져오기가 실패하면 새로 만든 메인과 인스턴스를 함께 되돌린다.

## 호환성·이관·복구

포크는 이 커밋과 부모의 변경 경로를 대조해 적용할 수 있다. 캐러셀 CMS나 외부 계정 연결은 필요하지 않다. 원본 화면과 사설 영수증은 로컬에 보존한다.

## 검증과 미검증

커밋은 Node 테스트 3개와 Python 테스트 2개를 추가했다. Node 테스트는 새 graph ID에서도 메인 하나를 공유하는지, 모양이 달라진 패밀리를 쓰기 전에 거부하는지, 실패 시 새 메인과 인스턴스를 제거하는지 확인한다. 실측 로그에서 Python 18개와 Node 29개가 통과했다. 실제 캡처 graph를 컴파일하면 shared_image_main_count가 1이었다. Figma 적용 후 읽기에서는 메인 1개와 인스턴스 3개, carousel `current`를 확인했고, 상태별 편집 가능 레이어 수는 40/42/40/36으로 수정 전과 같았다. 재사용 적용과 이후 다시 읽기도 같은 결과였다. 상태마다 다른 이미지나 한 화면에 같은 이미지가 여러 번 나오는 경우는 공유 대상이 아니며, 이번 표본에서는 확인하지 않았다.

## 한계와 후속 개선

여기서 확인한 결과는 해당 입력과 검증 범위에 해당한다. 브라우저의 연속 스크롤 관성이나 물리 모바일 기기의 동작은 별도의 관찰이 필요하다.
