# feat: share a component main when only its width differs

## 문제와 계기

같은 구조의 컴포넌트가 화면 너비만 달라도 Layout main이 늘었다. 기준 76a2d2b73a1d71631abe6f717073d15068c08155의 oracle은 `supported width uses must share one main`으로 실패했다.

## 결과 동작

root 너비 120·200·240은 한 main을 공유하고 각 instance의 너비·높이·토큰 fill은 원본과 같다. 자식 transform이 이동하거나 높이가 다르면 별도 Layout main을 유지한다. 다시 실행하면 instance ID와 main ID가 유지된다.

## 변경 파일과 인터페이스

`figma-bridge/semantic_components.js`의 `supportedRootWidth`만 공유 조건을 나눈다. 자식의 relativeTransform과 visualProfile, root 높이는 fingerprint에 남긴다. 안내 문서는 docs/development-roadmap/CURRENT_STATE.md, RD-01 feature.md, tasks.md다. 검사 파일 blob은 기준과 같다.

## 설계 이유와 출처

instance resize가 root 너비를 재현하므로 그 값만 새 main의 이유가 되지 않는다. 자식 크기·transform과 높이는 Auto Layout으로 추정해 지우지 않고 기존 분리를 유지한다. RD-01 설계서의 재사용 분류를 따른다.

## 호환성·이관·복구

semantic key, 선언된 variant props, 재실행의 unchanged 경로를 유지한다. 합칠 수 없는 기하 차이는 Layout 변형으로 남는다. 사용자 instance를 detach하지 않는다.

## 검증과 미검증

종료 게이트가 임시 아카이브에서 기준 oracle 종료 코드 1, 대상 640ff8c1a0ae1f185a60be5284558d6e7c914deb 종료 코드 0을 다시 실행했다. `tests/test_semantic_component_reuse.cjs`와 variant set 반지름 회귀도 통과했다. 실제 Figma 렌더와 속성 패널은 관찰하지 않았다.

## 한계와 후속 개선

지원 차이는 root 너비뿐이다. 자식 너비나 위치 차이를 추정해 합치지 않는다. 선언된 variant 축과 사용 설명은 아직이다. 61개 회귀 전체와 실기기 관찰은 이 변경의 완료 범위가 아니다.
