# test: pin authenticated historical restoration

## 문제와 계기

consumer가 과거 source A의 정확한 revision/artifact를 참조하는 동안 active source가 B로 교체된 뒤 다시 A를 준비하면, 새 session으로 재생성한 bundle과 인증된 retained A를 혼동할 수 있다. 실패한 교체가 고아 task 디렉터리나 catalogue 변경을 남기는지도 검사해야 했다.

## 결과 동작

새 oracle은 현재 원본이 A로 복원되고 active B의 expected revision을 제시했을 때 retained A의 row·bundle 바이트·revision을 정확히 되살리도록 요구한다. consumer edge는 그대로이며 task 디렉터리가 중복 생성되지 않아야 한다. 제품 구현 변경은 없다.

## 변경 파일과 인터페이스

[finalize_historical_restore.py](../../../tests/finalize_historical_restore.py)를 추가했다. 실제 prepare CLI로 A admission → consumer의 A pin → B replacement → dependency_artifacts의 retained A → 원본 A 및 record/root를 제시한 guarded replacement를 실행한다. code.js/ui.html/manifest.json/input-record.json 바이트와 workspace snapshot을 비교한다.

## 설계 이유와 출처

복원의 권위는 catalogue가 보존한 인증 row와 exact artifact다. 디스크에 남은 미참조 .tasks bundle을 스캔하여 권위로 삼아서는 안 된다. 별도 fixture는 retained되지 않은 A를 다시 준비할 때 revision이 같아도 이전 artifact_dir를 재사용하지 않도록 요구한다.

## 호환성·이관·복구

원본 freshness, 명시적 record/root, 현재 active revision의 compare-and-swap 경계는 복원에서도 유지한다. stale 원본·누락된 root/record·옛 expected revision은 쓰기 없이 거절해야 한다. 실패 시 active B, 기존 바이트와 디렉터리 집합이 보존되어야 한다.

## 검증과 미검증

Git diff에서 exact row/bytes와 current freshness, consumer edge 보존, 실패 snapshot 불변성, 미참조 bundle 비권위 검사를 확인했다. rejection-atomicity 테스트는 성공하면 exact revival을, 실패하면 완전 불변성을 검사하고 별도 첫 테스트가 성공 복원을 필수로 요구한다. frozen 기준의 의도한 red와 후속 미커밋 제품 수정의 통과를 구분한다.

## 한계와 후속 개선

POSIX private workspace fixture이며 실제 Figma나 GUI를 구동하지 않는다. 후속 06a40a1은 macOS 임시 경로 alias에 맞춰 root 기대값만 canonicalize한다. 외부 서비스·동시 writer·native 생성의 제품 인수를 이 기준에 귀속하지 않는다.
