# macOS CI 실행기 부족에 대응

## 문제와 계기

[0.27.0 전체 검사 run](https://github.com/jonsoku-dev/figma-flow/actions/runs/43327581031)은 15분 동안 실행기를 받지 못해 취소됐다. 공식 annotation은 hosted runner가 작업을 가져가지 못했다고 기록하고 ARM macOS 실행기의 capacity constraint를 세 차례 알렸다. 어떤 제품 검사도 시작되지 않았으므로 이를 코드 assertion 실패나 local ARM 결과의 실패로 해석하지 않는다.

## 결과 동작

동일 macOS 15의 표준 Intel 실행기 `macos-15-intel`을 명시한다. workflow의 trigger·권한·job 이름·설치·빌드·sandbox·Python·Node·demo 검사 명령은 유지한다. 기존 `uname -m`의 x86_64 분기가 이미 고정한 Intel Codex 배포 파일과 SHA-256을 선택한다. 추가 서비스나 자체 호스트 접근을 만들지 않는다.

## 변경 파일과 인터페이스

첫 부모 `25b6f754a4798119defc65c5146d59e0d3f23467` 대비 [전체 검사 workflow](../../../.github/workflows/test.yml)의 `runs-on`과 [CHANGELOG](../../../CHANGELOG.md) 두 파일만 변경했다. manifest는 부모와 같은 0.27.1이며 태그는 아직 발행 전이다. 제품 Python/JavaScript, 앱 데이터, Figma workspace 등록과 runtime 코드는 변경하지 않았다.

## 설계 이유와 출처

[GitHub 표준 hosted runner 문서](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)는 `macos-15-intel`을 Intel macOS 실행기로 명시한다. 같은 OS 검사를 유지하면서 실제로 부족했던 ARM 공급 경로를 바꾸는 좁은 조치다. Linux로 옮겨 macOS sandbox 검사를 건너뛰거나 검사 성공 조건을 완화하지 않았다. 실행기 종류와 각 환경의 결과는 별도로 기록한다.

## 호환성·이관·복구

job/check 이름이 같아 기존 결과 추적을 유지한다. Python·Node와 Codex CLI 버전·체크섬 고정도 보존했다. 아키텍처별 의존 패키지는 새 실행기에서 정상 설치·빌드되는지 원격 결과로 확인해야 한다. 필요하면 `runs-on`만 명시적으로 바꿀 수 있지만, 변경하지 않은 코드의 ARM local 검증을 원격 Intel 성공으로 대체해서 표현하지 않는다.

## 검증과 미검증

모든 workflow YAML을 local parser로 읽었고, 새 label과 기존 x86_64 Codex 배포 분기가 함께 남아 있음을 확인했다. 새로운 원격 실행은 이 제품 소스와 후속 Wiki 발행을 push한 뒤 판정한다. 이전 clean ARM local 결과는 Python 1,107개(2 skip), Node 299개(1 skip), 별도 finalize 74개·design 16개·PostgreSQL 58개·package 4개·demo 2개였으며 해당 0.27.0 소스의 근거다. 이것만으로 현재 Intel CI가 성공했다고 주장하지 않는다.

## 한계와 후속 개선

Intel hosted runner도 외부 서비스이므로 공급·시작 시간을 보장하지 않는다. 실패하면 실제 annotation과 job log를 먼저 확인한다. 이 변경은 대기 시간의 측정된 개선 배수나 새로운 지원 플랫폼을 약속하지 않는다. 최종 배포·설치·native runtime 판정은 CI 성공과 구분한다.
