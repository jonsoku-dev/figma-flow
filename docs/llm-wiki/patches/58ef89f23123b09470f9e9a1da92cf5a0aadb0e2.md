# 큰 Design 읽기 자동 수신과 모바일 인계 파일 수정

## 문제와 계기

20,421개 노드를 읽은 Figma 페이지가 일반 읽기 32 MiB와 요청 40 MiB 한도를 넘어 수동 저장이 필요했다. 빈 이미지 참조가 있는 페이지는 인계 파일을 만들지 못했고, 컴포넌트 인계에서는 긴 해시가 본문 너비를 늘렸다.

## 결과 동작

제품 소스 `58ef89f23123b09470f9e9a1da92cf5a0aadb0e2`은 성공한 대용량 읽기를 해당 claim의 릴레이 결과로 저장한다. 오프라인 팩은 유효한 래스터 참조를 보존한다. 컴포넌트 내용 뒤에서 제외한 에셋을 펼쳐 볼 수 있다.

## 변경 파일과 인터페이스

`tools/figma_control.py`, `figma-bridge/workspace_transport.js`, `figma-bridge/workspace_control.js`가 전송·접수 계약을 구현한다. `tools/native_handoff.py`가 이미지 참조와 HTML을 만든다. 한도와 작업 경로는 RD-07 및 Starter 명세에 기록했다.

## 설계 이유와 출처

일반 계약은 이전 결과 형식을 그대로 사용한다. 결과가 일반 한도를 넘은 성공한 read 작업에만 raw 64 MiB·전체 요청 80 MiB의 별도 경로를 사용한다. Figma 파일과 페이지, claim·revision 검증은 기존 결과 처리기를 공유한다.

## 호환성·이관·복구

로컬 릴레이를 수정한 소스에서 시작하고 등록된 작업공간을 refresh한 뒤 같은 플러그인을 다시 연다. 기존 준비 작업과 플러그인 ID를 유지한다. 인계 파일은 이전 근거를 덮지 않고 새 폴더에 생성한다.

## 검증과 미검증

실제 Figma Desktop에서 47,446,974바이트의 읽기와 토큰 전용 읽기를 자동 수신했다. 실제 웹 계산값이 있는 같은 그래프와 대조해 메인 하나, 인스턴스 두 개, 문구와 배경 토큰을 확인했다. 검증용 노드·계정·로컬 경로는 공유 기록에 포함하지 않았다.

## 한계와 후속 개선

이 변경은 읽기 결과의 용량을 한정한다. 큰 쓰기 결과에는 일반 한도를 적용한다. 모바일 결과는 브라우저 CSS 뷰포트 기준으로 확인하며 물리 장치와 유료 Dev Mode는 별도 인수 항목이다.
