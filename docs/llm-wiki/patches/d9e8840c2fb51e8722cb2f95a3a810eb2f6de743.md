# test: synchronize runtime drift observation

## 문제와 계기

affected-tests의 runtime drift 회귀가 0.4초 고정 timer로 입력을 바꿨다. 부하에 따라 변경이 preflight 전에 일어나면 제품은 receipt 없이 안전하게 거절했지만 테스트는 receipt.json을 읽다 FileNotFound로 실패했다. 의도한 실행 중 drift와 타이밍 오류를 구분해야 했다.

## 결과 동작

검사는 최대10초 동안 drift/node-tests 디렉터리 생성을 기다린 뒤 입력을 변경한다. ready/mutated Event로 실제 실행 준비와 변경 완료를 확인하고 stop 및 thread.join으로 worker를 정리한다. 이후 nonzero 결과와 receipt의 drift=true를 계속 요구한다.

## 변경 파일과 인터페이스

[test_affected_tests.py](../../../tests/test_affected_tests.py)만 변경했다. time import와 bounded polling thread를 추가하고 고정 Timer를 제거했다. run_cli(drift,--all,--run) → 실행 준비 디렉터리 → a.txt 변경 → runtime drift receipt 경로이며 제품 affected-tests 도구 소스는 변경하지 않았다.

## 설계 이유와 출처

preflight 거절 자체는 정상적인 안전 동작이므로 이를 제품 오류로 고치지 않는다. 검사 목적에 맞게 preflight 뒤 실행 중에 변경을 주입하고, 준비나 mutation이 없으면 assertion으로 분명히 실패시킨다. 무한 대기와 thread 누수를 피하기 위해 monotonic deadline 및 finally 정리를 사용한다.

## 호환성·이관·복구

기존 runtime drift 거절과 receipt 검사는 유지한다. 뒤의 skipped test fixture, nonzero 결과와 skip 판정도 바꾸지 않는다. 제품 trust boundary·source fingerprint·receipt 생성 규칙을 완화하거나 누락 receipt를 성공으로 처리하지 않는다.

## 검증과 미검증

Git diff에서 고정0.4초 timer 제거와 Event/10초 handshake/join, nonzero 및 drift assertion 보존을 확인했다. 상위 세션의 focused 검사는 worker3회와 primary1회 통과했다. 앞선 전체 Python1107 실행의 실패2개(skip2)는 이 timing 문제와 suite 도중 version 제품 수정에 따른 trusted runtime source changed였다. 안정된 full rerun은 진행 중이므로 통과로 바꾸지 않는다.

## 한계와 후속 개선

실행 준비 디렉터리를 관찰하는 bounded handshake는 이 fixture의 race를 좁히며 모든 스케줄러·극단적 부하를 보증하지 않는다. 준비나 변경이10초 내 없으면 명시적으로 실패한다. focused pass와 전체 suite 완료, 실제 GUI/native 진단은 별도 근거로 구분한다.
