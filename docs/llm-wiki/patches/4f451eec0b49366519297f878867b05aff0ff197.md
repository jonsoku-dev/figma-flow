# feat: store a server operation journal on the existing request record

## 문제와 계기

기준 aa0822c58b548c0b61e33874bada12ce4e2403bf는 요청 기록에 lifecycle journal이 없어 `server lifecycle journal must be stored with the operation`으로 실패했다.

## 결과 동작

enqueue는 operation_id를 요청 id로 정하고 queued 사건을 기존 요청 파일에 넣는다. poll은 claimed를 덧붙이고, result는 result-received를 덧붙인다. 복구된 읽기는 recovery_of에 원래 operation id를 두고 reconciled을 더한다. claim 후 timeout은 uncertain을 더하고, claim 전 timeout은 queued만 남긴다. 클라이언트가 보낸 operation ID는 결과 필드에서 거절된다. lifecycle 필드가 없는 요청은 단계를 만들지 않으며, lifecycle_version이 1이 아니면 claim하지 않는다. native-started는 기록하지 않는다.

## 변경 파일과 인터페이스

tools/figma_control.py의 enqueue, poll, result, active에 record_phase와 validate_lifecycle을 연결했다. docs/development-roadmap/RD-08-operation-lifecycle/tasks.md에 기록 범위를 적었다. tests/test_rd08_operation_journal.py blob은 기준과 같다. 새 queue나 상태 파일은 만들지 않았다.

## 설계 이유와 출처

RD-08은 기존 private request에 versioned lifecycle 필드를 붙인다. 시간의 역할은 표시이고, 식별은 operation_id와 recovery_of다. native-started는 인증된 runtime의 명시적 사건이 있을 때만 다음 단위에서 받는다.

## 호환성·이관·복구

lifecycle 필드가 없는 기존 요청은 claim과 result를 그대로 처리한다. 복구는 새 읽기 요청에 recovery_of를 두고 원래 영수증 바이트는 바꾸지 않는다. uncertainty blocking과 recovery_read 판정은 유지된다.

## 검증과 미검증

종료 게이트가 기준 aa0822c58b548c0b61e33874bada12ce4e2403bf의 종료 코드 1과 대상 4f451eec0b49366519297f878867b05aff0ff197의 종료 코드 0을 다시 실행했다. 같은 구현에서 전이 fixture와 기존 제어 검사를 합친 32개도 통과했다. 실제 Figma 읽기, 서버 재시작, 플러그인 재실행, 화면 단계 표시는 관찰하지 않았다.

## 한계와 후속 개선

이 단위는 native-started 전달을 만들지 않는다. 화면 조회와 legacy/unknown 구분은 다음 단위다. AC의 실제 표시는 통과로 기록하지 않는다.
