# test: pin bounded large-read request rejection

## 문제와 계기

큰 native readback을 위한 새 request 용량에 비해 기존 transport의 over-cap fixture는 옛 12/16 MiB 기준이었다. 정상 용량 거절 기대와 새 경계의 초과 거절을 구분해야 했다.

## 결과 동작

raw readback은 32 MiB+1, envelope은 2-byte UTF-8의 é를 20 MiB+1문자로 만들어 40 MiB를 초과하도록 요구한다. 둘 다 fetch 전에 거절하고 앞선 정상 poll 외에 추가 전송이 없어야 한다. 제품 제한을 바꾸는 커밋은 아니다.

## 변경 파일과 인터페이스

[finalize_lifecycle_transport.cjs](../../../tests/finalize_lifecycle_transport.cjs)의 생성 payload 길이 두 곳만 바꿨다. 기존 controlRequest(result/poll) → UTF-8/request guards → fetch 미도달 검사 경로를 사용한다.

## 설계 이유와 출처

문자 수와 UTF-8 byte 수는 다르다. é fixture는 envelope 40 MiB 경계를 실제 byte로 초과하도록 하고 raw JSON 32 MiB 경계와 별도로 검사한다. 옛 용량에 따른 잘못된 실패 대신 새 유한 계약의 초과 거절을 고정한다.

## 호환성·이관·복구

endpoint, Bearer 인증, route/origin allowlist, fetch 전 거절, timeout의 기존 assertion은 유지한다. response 16 MiB 계약은 변경 대상이 아니다. 새 request 32/40 MiB 계약은 별도 capacity oracle과 제품 구현으로 연결한다.

## 검증과 미검증

Git diff에서 12→32, é의 8→20 MiB+1 두 줄만 바뀐 것을 확인했다. 허용 경계와 실제 HTTP 저장은 d2e1b38 기준이 다룬다. 이번에는 실행하지 않았으며 이 검사 보정을 제품 transport 성공이나 native 인수로 보지 않는다.

## 한계와 후속 개선

이 fixture는 초과 거절만 다루며 최대 근처의 정상 수신·저장이나 response 크기를 단독으로 증명하지 않는다. 실제 Figma replay와 R7 전체 결과는 별도 근거가 필요하다.
