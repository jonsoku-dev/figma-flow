# e3bb050 · fork가 이어 가는 패치 지식과 0.26.1 검증표

## 문제와 계기

사용자는 별도 fork에서 개선하는 사람이 패치의 원인·인터페이스·검증 한계를 알 수 있도록 짧은 CHANGELOG와 내장 LLM Wiki를 함께 요구했다. canonical Git 기록만 보면 삭제 전 계보39개가 누락되고, 과거 성공 문구만 복사하면 현재 검증으로 오해할 수 있었다. 기존61개 회귀 케이스도 계획과 부분 실행 근거의 구분이 필요했다. 출처는 이 커밋의 첫 부모 `0bd817701f3df66673e314007f768a6de404fd78` 대비 실제 diff다.

## 결과 동작

전체 Git 조상의 커밋·부모·tree·변경 파일·diff 해시·당시 버전과 태그를 수집한다. 짧은 CHANGELOG에서 버전 대조표와 전체 SHA별8항목 기록으로 이동한다. 최초 이관에서 canonical43개와 보존 계보39개를 작성했고, 이 통합 커밋부터 추가 기록한다. 사람이 작성한 본문은 sync가 보존하며 빈 항목·누락·출처 불일치·깨진 링크는 verify가 거절한다. 개선 게이트는 실제 base 실패와 target 통과를 임시 Git 아카이브에서 재실행한다. 같은 명령명으로 검사 내용을 약하게 바꾸는 반례를 막기 위해 명령 파일의 Git blob과 모드를 고정한다.

## 변경 파일과 인터페이스

`tools/patch_knowledge.py`의 `inventory/sync/verify --ref`와 `figma-flow-patch-catalog-v1`이 canonical 기록을 관리한다. 기본 verify는 기록되지 않은 미커밋 제품 변경을 거절하며 `--committed-only`는 명시적인 역사 감사다. `tools/patch_knowledge_legacy.py`는 별도 보존 계보를 수집·검사하고 원본 Git이 없는 fork에서는 structural-only다. `tools/patch_knowledge_check.py gate <proposal> --execute`는 전체 base/target, 허용 변경 범위, 고정된 검사 파일, 예상 실패 문자열과 각 인수 조건을 검사한다. 프로세스·시간·출력·아카이브 크기를 제한하고 하위 프로세스를 정리한다. 세 대응 테스트 모듈, `skills/patch-knowledge/SKILL.md`, `AGENTS.md`, 읽기 권한의 `.github/workflows/patch-knowledge.yml`이 연결된다. `docs/llm-wiki/`는 계약·결정·개선 형식·통합 절차·버전/상세/보존 기록을 제공한다. 두 plugin manifest와 README·통합 가이드는0.26.1로 갱신했다. `specs/regression-program/cases.json`·계획·스펙 인덱스는61개 케이스에183개 해시 근거와 verified/remaining scope를 연결한다.

## 설계 이유와 출처

별도 서버·LLM API·LangGraph·hook을 추가하지 않고 기존 Git과 Python 표준 라이브러리로 fork의 독립 실행을 유지했다. 전체 SHA는 fork의 같은 버전 문자열을 구분하고, 별도 legacy 목록은 현재 canonical 조상과 옛 보존 계보를 혼동하지 않게 한다. 삭제 전 계보의 마지막 tree와 canonical 최초 import tree가 같다는 Git 객체 대조로 코드 이관을 확인했으며, 이 사실을 옛 브랜치의 모든 실행 성공으로 확대하지 않는다. Wiki의 글이나 상태값은 실행 권한·현재 제품 성공 증거가 아니다. 검사 파일 내용 변경으로 제품 수정 없이 통과한 독립 반례가 blob/mode 고정의 직접 원인이다.

## 호환성·이관·복구

기존 graph·Figma workspace·plugin ID·사용자 노드를 변경하지 않는다. 과거 기록에 없는 버전·이유·실행은 미상 또는 미검증으로 남긴다. sync는 수동 본문을 보존하며 catalog freshness가 어긋나면 실제 diff를 확인한 뒤 다시 기록한다. 검사 기준 변경이 필요하면 독립 기준 커밋을 먼저 보존하고 별도 구현 diff를 검사한다. 현재 source commit은 자신의 SHA를 같은 커밋에 기록할 수 없으므로 뒤의 Wiki/CHANGELOG 전용 발행 커밋을 허용한다. 그 발행에 제품 코드·테스트·정책을 섞으면 오래된 catalog로 통과하지 않는다. Git 없는 ZIP에서는 원본 객체 검증을 할 수 없어 전체 clone이 필요하다.

## 검증과 미검증

통합 소유자가 동결한6개 도구/테스트 파일의 SHA를 전후 대조한 상태로 Python 전체1,058개 중1,056개 통과·2개 건너뜀, Node214개 중213개 통과·1개 건너뜀, 데모2개 통과를 확인했다. Wiki41개 검사는 이 Python 집계에 포함된다. 별도 독립 재현에서 검사 파일만 낮춘 경우는 실행 전 exit1로 거절했고, 같은 검사 파일과 실제 제품 수정은 base AssertionError/target exit0으로 통과했다. 보존 계보39개는 원본 bundle의 Git 객체와 대조했고82개 기존 본문 재동기화는 바이트를 유지했다. 새 기록 발행 시 기본 verify·legacy verify·Wiki 검사를 다시 실행한다. 이 커밋 시점에0.26.1 원격 CI·태그·ZIP·설치 갱신은 아직 실행 전이다. 기존 사진/글꼴의 실제 브라우저·Figma 관찰은 이전 작업 근거이며 Wiki 검사가 새로 관찰한 결과가 아니다.

## 한계와 후속 개선

회귀61개 전체 케이스는 모두 unverified이며183개 부분 근거의 존재를 전체 인수 통과로 세지 않는다. 소유자 로컬 원본은 배포하지 않아 fork에서는 재실행이 필요하다. 실기기가 없고 실제 데스크톱 사용자 첨부 UX는 미검증이다. 검사 파일 고정은 의미상 충분한 인수 기준이나 OS 격리를 증명하지 않으며 검토한 실행 코드는 호스트에서 실행된다. Wiki·스킬은 호스트가 다음 턴을 계속 실행하도록 강제하지 않는다. branch protection과 외부 계정 권한은 변경하지 않는다. CSS 간접 의존성 추적과 대량 이미지 payload·복구/동시성 검증은 다음 실행 범위로 남긴다.
