# 포화된 이전 인덱스의 원본 요청 재발견

커밋 `44ffbe810f042ed5b2b0cc31a88a2732df2b6883`

## 문제와 계기

정상 RC1 writer가 활성 포인터 하나를 누락하고도 요청 파일을 남길 수 있었다. 이를 찾지 못하면 같은 파일에 두 번째 작업을 접수한다.

## 결과 동작

표시가 없는 이전 포화 인덱스에서 status 또는 접수가 미종결 요청을 대조한다. 복구 가능한 원본 ID와 claim을 유지하고, 과밀 상태에서는 ID 목록과 복구 안내를 제공한다.

## 변경 파일과 인터페이스

tools/figma_control.py의 인덱스 읽기·쓰기와 claim 조회를 보강했다. specs/codex-relay의 슬롯 계약과 직접 checked by 간선에 일반·이관 검사를 연결했다.

## 설계 이유와 출처

진행 건을 지우거나 다른 ID로 대체하면 기존 승인 및 영수증과 연계할 수 없다. 정상 폴링은 요청 이력을 순회하지 않는다. 초과 건을 보류할 때는 최초에 확인한 ID만 이후 상태 조회에서 읽는다.

## 호환성·이관·복구

기한이 지난 쓰기는 원래 uncertain 영수증과 쓰기 보호를 유지한다. 제때 도착한 과거 claim 결과에도 기존 claim·세션·scope 검사를 적용한다.

## 검증과 미검증

실제 RC1의 65개 공개 enqueue 결과에 대해 RC2가 빠진 원래 ID를 조회하고 중복을 차단했다. 빈자리가 생긴 뒤 같은 ID를 한 번 인수하고 결과를 저장했다. 표준 요구사항 그래프 증인도 통과했다.

## 한계와 후속 개선

이미 시작한 작업의 실제 문서 변경 여부를 이력만으로 단정하지 않는다. 결과가 불확실하면 같은 파일·페이지에서 읽어 확인한다.
