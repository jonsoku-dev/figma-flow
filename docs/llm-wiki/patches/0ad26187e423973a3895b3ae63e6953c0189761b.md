# test: bound readable board native lookups

## 문제와 계기

새 readable board의 각 note와 annotation마다 children을 다시 훑으면 native semantic-key/child-id getter 작업이 이차적으로 증가한다. 실제 공유 authoring 함수의 작업량을 독립 기준으로 고정할 필요가 있었다.

## 결과 동작

24/48 notes의 ensureDesignNoteBoard와 readable ensureNativeAnnotations에 선형 예산을 요구한다. entry 본문·board 부모·target hyperlink를 유지하며 stale owner, duplicate, 도중 실패, font await 중 동시 편집은 계속 거절한다. 제품 변경은 없다.

## 변경 파일과 인터페이스

[finalize_note_board_reads.cjs](../../../tests/finalize_note_board_reads.cjs)를 추가했다. [API-shaped host](../../../tests/helpers/finalize_native_build_reads.cjs)에서 실제 ensureDesignNoteBoard/ensureNativeAnnotations를 호출하고 semanticKey getter, board.children materialization, child.id getter를 센다.

## 설계 이유와 출처

fresh board는 semanticKeyReads≤4×(sourceNodes+notes), annotation은 childIdReads≤4×notes와 childrenReads≤4를 요구한다. 반복 native getter가 비용의 원인이므로 하드웨어에 좌우되는 시간이 아닌 직접 작업량을 측정한다. 소유권 검사를 생략해 예산만 맞춰서는 안 된다.

## 호환성·이관·복구

기존 board의 owner 불일치와 duplicate child는 entry를 덮어쓰지 않는다. 신규 styleText의 다섯 번째 호출 실패는 새 board만 rollback하고 기존 target을 보존한다. font await 중 사용자 편집은 concurrent conflict로 남긴다. schema/API는 바꾸지 않는다.

## 검증과 미검증

Git diff는 예산 검사 2개와 보호 검사 4개, 총 6개 테스트를 추가한다. 상위 세션의 최초 예산 검사 2개는 의도한 red였다. 후속 미커밋 제품 수정 후 관측은 fresh semantic getter 649→50 및 2449→98, annotation child-id 1224→98이었다. 이를 기준 커밋 자체의 제품 성공으로 소급하지 않는다. 이번 기록 작업은 정적 대조만 했다.

## 한계와 후속 개선

API-shaped host의 getter 수는 실제 Figma 지연·메모리·렌더링 성능 측정이 아니다. native 재실행이나 GUI 인수를 완료로 표시하지 않는다. R7 native 실행은 진행 중이므로 전체 성공은 미확정이다.
