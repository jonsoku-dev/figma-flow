# 93ec9aa · relay 영수증 중단 복구와 새 요청 보존

## 문제와 계기

출처 `93ec9aae6ed9e16508b8a9b600ec6a1bedc8e779`의 이전 relay는 고정 이름 임시 영수증이 남으면 새 저장을 막을 수 있었다. 실행 전 영수증 읽기·초기 claim 실패도 실행 후 불확실성과 구분할 필요가 있었다.

## 결과 동작

매 저장마다 고유한 비공개 임시 파일을 만들고 원자 교체한다. 이전 중단의 임시 파일이 있어도 새로운 요청은 처리한다. 실행 전 claim 저장 실패는 행동을 시작하지 않았다는 오류다. 실행이나 최종 영수증 저장 실패는 durable claim을 uncertain으로 남기고 동일 요청 재시도가 중복 전송하지 않게 한다.

## 변경 파일과 인터페이스

`tools/workspace_chat.py`의 `ChatServer.save_ledger()`는 `tempfile.mkstemp`와0o600 권한을 사용한다. `perform()`은 실행·최종 저장을 같은 예외 범위에서 다루고 `ChatHandler`는 결과 상태로 실제 부작용 가능성을 구분한다. `tests/test_workspace_chat.py`에는 오래된 임시 파일·실행 전 실패·재시도 검사가 추가됐다.

## 설계 이유와 출처

초기 claim을 먼저 보존해야 전송 후 응답 저장이 실패해도 무작정 다시 전송하지 않는다. 고유한 임시 파일은 이전 프로세스 잔여물과 새 저장의 충돌을 없앤다. 이는 실제 diff에서 확인되는 구조이며 전체 당시 논의는 미상이다.

## 호환성·이관·복구

기존 chat-requests.json과 requestId 재사용 계약은 유지한다. 오래된 임시 파일은 새 요청을 막지 않으며 임의로 지우지 않는다. uncertain 요청은 원래 채팅의 실제 상태를 확인한 뒤 처리한다. 초기 claim 실패의 명백한 미시작은 전송 재실행과 구분한다.

## 검증과 미검증

추가 테스트는 subprocess를 대역으로 써 호출 횟수·재시도·파일 권한을 검사한다. 테스트 코드 존재가 당시 실행 통과나 실제 Codex 전달 성공의 증거는 아니다. 이 Wiki 보완에서 그 네이티브 실행을 재현하지 않았다.

## 한계와 후속 개선

외부 실행의 성공과 영수증 저장은 원자 트랜잭션이 아니므로 불확실 상태가 남을 수 있다. 이 상태를 자동 성공으로 해석하지 않는다. OS별 실제 채팅 열기·큐 전달은 해당 호스트에서 별도 관찰해야 한다.
