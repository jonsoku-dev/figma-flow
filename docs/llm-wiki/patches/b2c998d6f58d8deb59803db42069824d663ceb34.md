# docs(roadmap): start P2 wave 1 with execution contract and in-progress invariant

## 문제와 계기

`p0-reference-safety`가 `verified`가 되자 `p2-rights-cleared-fixture`와 `p2-read-performance-baseline`이 `next-ready`가 됐다. 두 작업을 시작하려면 그래프 상태, 실행 계약, 인수 경계가 필요했다. 기존 로드맵 검사는 `next-ready`가 비어 있고 모든 작업이 충족 상태가 아니면 실패했으므로, 진행 중 작업만 있는 그래프를 거절했다.

## 결과 동작

커밋 `b2c998d6f58d8deb59803db42069824d663ceb34`는 두 노드를 `in-progress`, `evidence_status: pending-root-live-evidence`로 바꿨다. 후속 FAQ, 복합 렌더 fidelity, incremental read 노드는 `proposed`로 남았다. 새 [P2 1차 실행 계약](../../next-roadmap/p2-wave1-acceptance.md)은 의존성 그래프, 최소 데이터 형태, 인수 항목, 상태 승격 규칙, root 실측 절차를 정한다. 이 커밋은 증거를 기록하지 않는다.

## 변경 파일과 인터페이스

`docs/next-roadmap/backlog.graph.json`(두 노드의 `status`, `evidence_status`, `spec_refs`, `acceptance`, baseline `commands`에 기존 `rd06_full_getter_ledger.cjs`·`rd06_read_comparison.cjs`), `docs/next-roadmap/capability-review.md`·`README.md`(계약 링크와 불변식 설명), 새 `docs/next-roadmap/p2-wave1-acceptance.md`, `tests/test_next_roadmap_backlog.py`. 검사의 `validate_backlog_graph`는 `in-progress` 작업이 미충족 `depends-on` 선행, `verified*` 근거 표시, 없는 `proof_refs`를 가지면 오류를 낸다. 실제 그래프 검사는 `next-ready`, `in-progress` 작업, 전체 충족 중 하나가 있으면 진행 가능으로 본다. 링크·이식성 검사 대상에 새 문서를 넣었다.

## 설계 이유와 출처

[로드맵 README](../../next-roadmap/README.md)의 `next-ready` 정의는 `proposed` 작업만 센다. 시작한 작업을 `proposed`로 두면 상태가 거짓이 되고, `next-ready` 목록을 검사에 고정하면 그래프 정본이 검사로 옮겨 간다. 그래서 진행 중 작업을 진행 경계로 인정하고, 선행 미충족 착수와 근거 위장을 새로 거절했다.

## 호환성·이관·복구

`status_vocabulary`에 이미 `in-progress`가 있었다. 제품 소스와 동결 검사(`rd06_*`, `test_graph_sync.py`, `reference_distribution_guard.py`) blob은 바뀌지 않았다. 되돌리면 두 노드는 `proposed`·`unstarted`로 돌아간다.

## 검증과 미검증

`python3 -B -m unittest tests.test_next_roadmap_backlog` 3개 통과. 기준 커밋의 검사는 새 그래프에서 진행 경계 단언 1건으로 실패했고, 새 `in-progress` 분기를 제거한 변이 검사도 1건 실패했다. `node --test tests/rd06_full_getter_ledger.cjs tests/rd06_read_comparison.cjs` 2개 통과, `tests.test_design_specialization` 통과, `reference_distribution_guard.py --worktree` `paths_only_clear`(`forbidden_paths=0`). 브라우저·Figma 실행과 두 작업의 구현은 이 커밋 범위가 아니다.

## 한계와 후속 개선

처음 계약은 P0 manifest schema를 기준으로 들었고 baseline 시간 샘플에 ledger getter 수를 넣었다. 독립 검토 후 [1214f48](1214f4848619f09cb1f625c5b3486ea71bc54aa1.md)이 이를 고쳤다. 두 노드의 `verified` 승격은 root가 통합 소스에서 직접 관측한 뒤에만 한다.
