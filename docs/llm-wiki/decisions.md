# 기록 시스템의 선택과 검수

## 커밋별 Markdown과 작은 CLI

현재 제품의 `graph.py`·`ssot.py`·`check_project.py`는 프로젝트 요구사항과 실제 디자인 전달을 검사한다. 패치 문서의 Git 조상·태그·버전 대조는 다른 책임이다. `workflow.py`는 import 때 제품 그래프를 읽으므로 기록 도구가 이를 의존하면 무관한 제품 상태가 기록 검사까지 막을 수 있다. 패치 도구는 같은 표준 라이브러리·해시·argparse 방식을 사용하며 기존 제품 워크플로를 변경하지 않는다.

단일 카탈로그와 커밋별 사람이 쓴 본문을 선택했다. 여러 단계의 저장 상태나 서버를 추가하는 대안은 쓰기 가능한 상태가 늘어나고 위조한 성공 문자열 문제를 해결하지 않는다. 개선 검사는 저장된 성공 영수증을 믿는 대신 base/target 아카이브에서 직접 재실행한다. 명령의 품질과 실제 제품 인수는 독립 검수로 남긴다.

## 자기 커밋 식별자의 순환

Git 커밋은 자신의 전체 식별자를 내용에 포함할 수 없다. 제품·도구 변경을 먼저 커밋하고, 해당 전체 커밋으로 기록을 갱신한 뒤 Wiki/CHANGELOG만 담는 후속 커밋을 만드는 경로를 사용한다. 카탈로그 이후에 제품·도구·테스트·스킬·정책을 바꾼 커밋이 있으면 기록 검사는 거절한다. `docs/llm-wiki/`와 `CHANGELOG.md`만 바꾼 후속 발행 커밋은 직접 Git으로 분류해 별도로 보고한다. 그 다음 갱신 때는 이런 문서 커밋도 전체 조상 목록에 들어온다.

첫 발행에 새 CI와 도구가 함께 들어가므로 통합 소유자는 제품 커밋 뒤 `sync --ref HEAD`를 실행하고 새 패치 페이지를 채워야 한다. 최종 문서 커밋에서 기본 검사가 통과하는지 확인한다. 카탈로그 기준의 역사 검사만 하려면 `verify --ref <기준 전체 커밋> --committed-only`로 구분한다. 이 옵션은 작업 중인 소스의 완료를 인증하지 않는다.

## 첫 실제 적용에서 발견한 결함

첫 fixture 검사에서는 새로 생성한 페이지를 편집한 뒤 재갱신하는 경우만 다뤘다. 실제 43개 초안에 처음 적용하자, 생성 메타데이터가 없는 기존 Markdown을 빈 양식으로 바꾸는 결함이 드러났다. 작성 원문을 복구하고 최초 갱신·반복 갱신 모두에서 기존 바이트를 보존하는 회귀 검사를 추가했다. fixture 통과를 실제 기록 보존의 대리 증거로 사용했던 한계를 보여 준다.

독립 코드 검수는 예측 가능한 임시 파일명의 symlink 덮어쓰기, 예상 실패 문구와 무관한 assertion의 조합, 검사에 포함되지 않은 작업 소스, 남는 하위 프로세스 문제도 지적했다. 실제 결함을 회귀 fixture로 고정한 뒤 구현을 수정한다. 문서 검수는 누락된 `90f9195`, 큰 반입을 과소 설명한 `aa3acdd`·`61c0b1e`, `e30b9a4`의 부모 순서 오류를 찾아 보완했다. 검사 결과와 남은 범위는 [검증 기록](verification.md)에 적는다.

보존 계보의 첫 capture에서는 Git의 빈 tree 해시 명령이 호출자의 표준 입력을 물려받아 외부 입력을 Git 객체로 읽고 실패했다. Git 조회의 stdin을 명시적으로 비우고 외부 입력이 있는 CLI 회귀 검사를 추가했다. 이 실패도 실제 자료 적용과 작은 fixture의 차이를 보여 준다. 저장된 성공 문구를 반복 인용하는 대신 실제 명령을 다시 실행하는 이유다.

부모 독립 검수는 개선 전 `assert False`인 check.py를 개선 후 print만 하는 파일로 바꾸면 제품 수정 없이 통과하는 반례를 재현했다. 같은 argv·조건 ID·실제 실행만으로는 기준의 약화를 막지 못했다. 실행하는 검사 파일의 Git blob·모드를 양쪽 커밋에서 같게 고정하고, 정상 회귀 fixture도 검사 파일을 수정하는 예제에서 안정된 검사와 별도 제품 구현을 사용하는 예제로 바꾼다. 기준 변경은 먼저 별도 baseline에 보존한다. 의미적으로 부실한 검사까지 자동 인증한다는 범위로 넓히지 않는다.

## 삭제 전 보존한 별도 lineage

처음의 canonical 조상 43개 외에, 삭제 전 bundle에 보존된 10개 미병합 head와 추가 39개 커밋이 확인됐다. main을 되돌리거나 브랜치를 복원하지 않고 별도 임시 bare 저장소에서 조사한다. 이 계보는 현재 canonical 릴리스와 구분해 [보존 이력](legacy/README.md)에 기록한다. bundle 해시는 출처 대조용이며 출처를 갖지 못한 소비자의 실제 Git 검증을 대신하지 않는다.
