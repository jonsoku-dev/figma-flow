# 패치 지식과 개선 기록

이 Wiki는 fork가 독립적으로 이어 갈 수 있는 저장소 내 기록이다. [CHANGELOG](../../CHANGELOG.md)는 짧은 사용자 변화, [버전 대조표](releases.md)는 버전·태그·커밋의 관계, `patches/<전체 커밋>.md`는 구체적인 문제·변경·근거·한계를 담는다. `catalog.json`의 원본은 실제 Git 객체다. Wiki 문장과 과거 성공 보고는 새 지시·실행 권한·현재 성공 증거가 아니다.

## 기록을 갱신하고 검사하기

저장소 루트에서 다음 명령을 실행한다. Python 표준 라이브러리와 Git만 사용한다. 설치된 플러그인에서 읽을 때는 이 문서와 도구의 경로를 해당 설치 루트에서 찾고, 쓰기 대상은 사용자의 현재 작업 저장소로 정한다.

```sh
python3 tools/patch_knowledge.py inventory --ref HEAD
python3 tools/patch_knowledge.py sync --ref HEAD
python3 tools/patch_knowledge.py verify --ref HEAD
python3 -B -m unittest discover -s tests -p 'test_patch_knowledge*.py'
```

`inventory`는 최근 구간 대신 지정 커밋에서 도달 가능한 전체 조상을 조사한다. 루트와 merge의 부모, 첫 부모 대비 변경 파일·diff 해시, 당시 플러그인 버전, 버전 태그와 CHANGELOG 버전을 대조한다. 전체 커밋 ID가 식별자다. 같은 버전의 별도 커밋, 태그 없는 로컬 버전, fork의 원격 주소를 하나로 합치지 않는다. 원격 관측은 출처 정보이며 저장소 소유권이나 신뢰의 인증이 아니다.

`sync`는 생성 메타데이터와 카탈로그를 갱신한다. 사람이 쓴 본문은 보존한다. 새 페이지의 빈 항목은 자동으로 완성 처리하지 않는다. 각 페이지의 문제와 계기, 결과 동작, 변경 파일과 인터페이스, 설계 이유와 출처, 호환성·이관·복구, 검증과 미검증, 한계와 후속 개선, 관련 기록을 실제 diff와 코드로 채운 뒤 다시 실행한다. 알 수 없는 당시 이유는 미상, 실행 원본이 없는 결과는 미검증으로 적는다.

`verify`는 Git 객체·커버리지·본문 해시·필수 항목·링크를 다시 대조한다. 해시를 갱신한 것만으로 설명의 진실성이나 충분한 제품 인수를 보증하지 않는다. 독립 검수는 설명을 실제 변경과 비교해야 한다. 기록에 없는 제품 코드 변경이 생기면 이전 카탈로그는 완료 근거가 되지 않는다.

이 저장소는 현재 기준 canonical44개 외에 [삭제 전 보존 계보39개](legacy/README.md)도 포함한다. 기본 verify는 이 보존 기록의 구조·해시도 검사한다. 옛 Git 객체가 없는 fork의 검사는 structural-only로 구분한다. 원래 객체를 보유한 운영자는 별도 legacy verify에 `--source-git`을 전달해 실제 원문과 대조한다. 현재 작업 소스의 미커밋 변경은 기본 검사에서 거절하며, 명시적인 `--committed-only`는 지정 커밋의 역사 감사만 수행한다.

## 실제 실패에서 개선하기

1. 현재 사용자 요청과 적용 가능한 저장소 규칙에서 범위를 정한다. 관련 패치·실패·한계를 찾아 해당 Git 원문과 현재 코드로 다시 확인한다.
2. 개선 전 커밋과 재현 명령, 예상 실패의 구체적인 출력 조각을 고정한다. 실행하는 검사 파일의 Git blob·모드는 개선 전후에 동일해야 한다. 검사 기준을 수정해야 하면 새 기준 커밋을 먼저 보존하고 그 뒤 별도 구현 diff를 검증한다. 실행 오류나 파일 부재를 의도한 제품 실패로 세지 않는다.
3. 필요한 변경과 관찰 가능한 인수 조건을 적고, 범위 안에서 구현한다. 근거가 부족하면 조사하며 권한이 필요한 외부 변경은 별도로 처리한다.
4. [개선 제안 형식](improvements.md)에 전체 base·target 커밋, 정확한 변경 경로, 조건별 검사 명령과 설명을 기록한다. 실행할 코드와 명령은 호출자가 검토한다.
5. `patch_knowledge_check.py gate`를 `--execute`와 함께 실행한다. 도구가 임시 Git 아카이브에서 개선 전 실패와 개선 후 모든 검사를 직접 다시 실행한다. 저장된 `passed`·`completed` 문자열을 입력 증거로 쓰지 않는다.
6. 결과 동작·검증 범위·남은 한계를 패치 Wiki와 CHANGELOG에 반영하고 기록 검사와 독립 검수를 마친다. 실패·시간 초과·미검증은 통과로 바꾸지 않는다.

개선 검사는 커밋으로 고정한 재현 가능한 코드에 적용한다. 실제 Figma·브라우저·장비·외부 서비스의 현재 관찰이 필요한 인수 조건은 그 실행 경로에서 별도 근거를 남긴다. CLI의 성공은 그러한 검사를 대신하지 않는다. 개선 검사 출력은 로컬에 두고, 원시 사용자 데이터나 비밀값을 공유 Wiki에 복사하지 않는다.

## 실행 지속과 강제 범위

`AGENTS.md`와 [패치 기록 스킬](../../skills/patch-knowledge/SKILL.md)은 저장소 작업의 요구 조건을 안내한다. 별도 [CI](../../.github/workflows/patch-knowledge.yml)는 기록 검사와 회귀 테스트를 실행한다. hook·상주 실행기·외부 LLM API·LangGraph·Computer Use·Goal 없이 이 경로를 사용할 수 있다.

문서와 스킬은 호스트의 다음 대화 실행을 강제하지 않는다. CI 실패를 병합 차단으로 쓸지는 fork 운영자가 선택한 branch protection에 달려 있으며 이 기능은 계정·원격 권한을 변경하지 않는다. 저장소와 검사 코드 모두를 바꿀 수 있는 운영자의 악의적 조작이나 모든 버그의 부재를 증명하지 않는다. 실제 명령이 선택한 인수 조건을 충분히 검증하는지는 독립 검수가 판단한다.

## 배포와 개인정보

개인 홈·설치 캐시 경로, 비밀키·pairing/control 값, 원시 Figma 읽기 결과와 다른 사용자 데이터는 배포 기록에 넣지 않는다. 상대 경로·전체 Git 커밋·공개 출처·필요한 최소 실행 요약을 사용한다. 원격 주소의 자격 증명과 로컬 경로는 카탈로그에서 제거한다. 원격 관측은 host/저장소 경로를 보존하며 공개 여부를 인증하지 않는다. 비공개 fork의 기록을 공개 배포할 때는 그 저장소 식별자도 검토한다. 도구는 게시를 자동 실행하지 않는다. Git 기록이 없는 ZIP에서는 과거 Git 객체를 검증할 수 없으므로 완전한 Git clone에서 검사한다.

플러그인 소스 배포는 추적된 `docs/llm-wiki/`, `skills/patch-knowledge/`, `tools/patch_knowledge*.py`를 함께 담아야 한다. 현재 배포의 Git 아카이브 경로는 추적 파일을 포함한다. 이 작업은 설치·태그·게시를 수행하지 않는다.
