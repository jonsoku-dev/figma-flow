# Codex에서 지시하고 Figma에서 확인하기

현재 Codex 대화가 요청, 방향 선택, 승인, 배경 설명, 결과 보고의 창이다. Figma에서 열어 둔 플러그인은 문서의 실제 값을 읽고 범위가 고정된 작업을 실행한다. 표시할 수 있는 내용은 연결 상태, 현재 파일·페이지, 선택한 레이어, 마지막 처리 상태와 연결 정보다.

| 사용자 행동 | 담당 | 인수 조건 |
|---|---|---|
| “방금 선택한 버튼 확인해 줘” | Codex가 `sessions`/`context`를 조회하고 준비한 read 작업을 실행 | 열린 파일 탭별 `session_id`로 인증된 Figma 세션의 파일·페이지와 선택 범위를 확인한다. 선택한 항목이 많으면 총수와 반환 범위를 표시한다. 실제 결과 JSON을 읽어 답한다. |
| “이 파일은 플랜 모름, 좌석 View로 설정해 줘” | Codex가 대상 파일 탭의 문맥(`--file-key`)과 저장 결과를 확인 | 세션·사용자·파일·페이지가 바뀌면 재확인한다. `ok`와 접수·만료·불확실을 구분한다. 저장소는 기존 플러그인의 `clientStorage`다. |
| 변경 요청이나 디자인 승인 | Codex에서 실제 지시를 확인하고 파일별 작업 슬롯에서 검사·실행 | 읽기 전용 선언, 잘못된 파일·페이지·버전, 파일별 `uncertain` 쓰기 보호 및 실제 Figma 권한을 기존 실행 경계에서 검사한다. 서로 다른 파일 탭은 동시 실행할 수 있으며 같은 파일 안에서는 직렬화한다. |
| 파일 확인·필요한 경우 캔버스에서 대상 선택 | Figma에서 같은 개발 플러그인을 탭마다 한 번 실행 | 플러그인 홈은 대화·설정 폼·작업 버튼 없이 상태를 표시한다. 제어 설정 누락, 서버 포트 미연결, 세대 불일치, 파일 키 없음은 원인별 진단 안내로 표시하며 `연결 정보`에 `플러그인 ID·포트·세대`를 제공한다. |
| 예제 생성 요청 | Codex에서 고정된 레시피를 native-edit로 준비하고 apply | 허용된 네 예제만 정확한 파일·페이지로 실행한다. 같은 레시피·소스·범위의 재적용 결과에는 기존 컨테이너 ID를 반환한다. |

준비 작업 목록·결과 영수증과 프로필의 사용 조건은 각 정본이 계속 소유한다. 릴레이는 사용자와의 대화나 자체 승인 기록을 만들지 않는다. 선택 이름·ID·유형과 프로필 선언은 인증된 로컬 제어에만 사용한다. 실시간 맥락은 시간과 세션에 따라 만료되며 과거 영수증은 별도다. 신규 작업 준비로 등록된 런타임 세대가 바뀌면 같은 플러그인을 다시 열어 새 세대를 확인한다.

400 × 300 뷰어는 연결 상태, 파일·페이지·선택 세 줄, 펼쳐 보는 상세 정보로 구성한다. 밝고 어두운 Figma 테마를 따르며 연결 상태는 색과 텍스트로 함께 표시한다. 사용자의 스킬 모음에서 상태 표시와 구분선 기준을, Muse에서 운영 화면의 정보 계층 사례를 참조했다. [스킬 모음의 UI 기준](https://github.com/jonsoku-dev/awesome-skills-jonsoku/blob/280d85a4d96316bbc176bd9595be33ab90d64b3f/design-rules/rules/anti-ai-slop-ui.md) · [Muse의 UI 사례](https://github.com/jonsoku-dev/muse-knowledge/blob/d623a280a298509fbe6ec376dda709c81475577e/inbox/2026-11-22-github-satnaing-shadcn-admin.md)

열린 Figma 탭마다 독립 `session_id`와 파일별 작업 슬롯·프로필 요청 사서함을 유지한다. 여러 파일이 동시에 열려 있을 때 Codex는 `figma_control.py sessions`로 전체 열린 탭을 확인하고 `--file-key`(또는 `--session-id`)로 대상을 지정해 병렬 작업한다. 프로필 선언은 해당 세션·파일·사용자 및 발행 세대에 묶인다.

### PC 작업공간 기억과 선택

기본 workspace 생성·제어·서비스 시작은 명시된 로컬 경로만 사용한다. 영구 목록에 추가하거나 저장된 메타데이터를 갱신하려면 `figma_workspace.py remember --workspace PATH`를 사용한다. `--default`가 있으면 해당 경로를 기본값으로 선택한다. 기존 파일의 형식이나 권한을 확인할 수 없으면 등록은 실패하며 기존 바이트를 보존한다.

`setup-status`는 명시한 경로, 유효한 PC 기본값, 유일한 유효 후보 순서로 선택한다. 여러 후보 중 선택이 필요하면 경로 지정과 기본값 설정 방법을 표시한다. 자동 조회는 영구 선택을 변경하지 않는다.

### 파일별 작업 포인터와 혼잡 복구

한 등록 작업공간은 최대 64개 파일의 최신 작업 ID를 보관한다. 1~128자 영숫자 파일 키를 지원하며 이전 단일 ID 포인터도 원래 파일에 연결한다. 같은 파일의 진행 중인 작업은 직렬화한다. 새 파일이 빈자리를 필요로 하면 가장 오래된 종결 작업의 포인터만 정리하고 원본 요청과 영수증은 ID로 계속 조회할 수 있다.

모든 슬롯이 진행 중이면 새 요청을 저장하기 전에 종료 코드 2와 상태 조회 방법을 반환한다. 명시적 `figma_control.py status`는 기한이 지난 작업을 종결하고, 인수된 쓰기의 결과가 불확실하면 보호 기록과 영수증을 보존한다. 메트릭스와 세션 조회는 저장된 상태를 변경하지 않고 기한 안에 있는 진행 작업만 보고한다.

이전 버전의 포화 인덱스에서 진행 중인 파일이 보이지 않으면 `figma_control.py status --workspace WORKSPACE --file-key FILE_KEY`로 확인한다. status와 새 요청 접수는 기존 요청을 대조해 누락된 원래 ID와 claim을 되찾는다. 모두 64개 슬롯에 들어가면 새 형식으로 저장한다. 진행 요청이 더 많거나 같은 파일의 작업이 겹치면 상태 응답에 원래 작업과 복구 안내를 표시하고 추가 접수를 보류한다. 기존 작업이 끝나거나 기한이 지나면 상태를 다시 확인한다. 보류 중에는 누락된 ID 목록만 재조회하며, 유휴 플러그인 폴링은 과거 요청 디렉터리를 순회하지 않는다. 이미 인수된 쓰기의 결과는 원래 claim으로 확인하고, 기한이 지난 쓰기는 기존 uncertain 읽기 복구 절차를 따른다.

### 이전 패널의 작업 보존

Codex가 같은 입력과 범위를 전달하고 실제 결과를 돌려받는지를 [기능별 대조표](parity-inventory.json)에 기록한다. 읽기와 쓰기, 일부 변경 선택, 기존 페이지 재사용과 새 복사본, 선택 레이어 메타데이터와 요청한 텍스트를 각각 구분한다. 연결·선택 표는 열린 뷰어의 메모리에만 유지한다. 서명된 작업 요청에 대한 결과 파일과 기존 파일별 기기 이력은 Codex에서 조회할 수 있다.
